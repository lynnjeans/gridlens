## 1. 产品概述与项目关系

Warm-up 的交付物是一个可以完整演示的研究助手。用户输入研究主题或问题，系统主动搜索候选资料；人工决定哪些资料可以进入知识库；用户随后通过 RAG（Retrieval-Augmented Generation，检索增强生成）获得有出处的回答，并把证据不足的问题转为后续研究任务。

Seen Ventures 主项目希望探索数据中心接入电网时，冗余要求、限电安排等条件与容量、接入时间之间的取舍；utility side 和 data centre side 的优先级仍待研究决定。Brief 将上述内容作为会继续调整的工作假设，而非固定规格。这个研究助手支持前期研究，并不直接实现主项目的容量探索产品。[B1，pp. 1–2]

| Brief 的前期要求 | Warm-up 如何支持 | 最终仍需人工完成的工作 |
| --- | --- | --- |
| 了解新西兰大型用户接入流程、参与方与延误 | 汇集官方流程资料，回答问题并显示出处 | BA/UX 与团队共同核实和绘制流程图 |
| 比较 utility side 与 data centre side 的需求 | 汇集双方公开证据，记录假设与缺口 | 结合访谈判断痛点和 champion，不由模型替团队拍板 |
| 盘点公开容量资料及格式 | 维护可搜索的来源目录和使用限制 | Data Analyst 核实数据是否适合后续分析 |
| 维护 shared research log | 保存发现、审核理由、问答引用和未解决问题，并导出 Markdown | 团队持续整理到共同使用的 research log |
| 第二周末提交 1–2 页 research note | 提供可追溯研究材料和开放问题列表 | 团队撰写结论、方向建议与待验证问题 |

上述前两周要求来自 brief 第 5 页。[B1] Brief 第 2 页列出的正式 engagement 起始日是 2026-10-19；本次 warm-up 的实际起始日尚未指定，因此计划使用 D1–D10，不自动套用该日期。

## 2. 问题与待验证假设

团队需要阅读政策、接入指南、技术文件、论文和行业报告。这些材料分散于不同机构网站，适用地区、发布日期与权威程度各不相同。单纯收集链接难以积累可复用知识，通用 AI 回答又不容易确认具体依据。

以下是本工具拟解决的研究流程问题，需通过实际使用验证，不能当作已完成的用户访谈结论：

1. **发现成本高**：同一问题需要多轮搜索，相关材料容易遗漏或重复收集。
2. **来源质量难判断**：官方要求、学术研究和供应商宣传可能被混为一谈。
3. **阅读结果难复用**：研究发现缺少原文位置、版本与审核记录。
4. **答案难核查**：模型可能给出看似合理但缺少依据的流程、数字或结论。
5. **下一步不清楚**：团队不知道问题尚未解决是因为没有资料、地区不匹配，还是知识库尚未覆盖。

两周内重点验证：该工作流是否能找到足够有用的资料；人工审核是否易用；基于批准资料的回答是否可靠；缺口提示是否能指导下一轮研究。不承诺已证明节省了多少时间。

### 3.2 优先级与实施边界

**P0 必须完成**：用户触发的自动搜索、候选列表、人工审核、HTML/文本型 PDF 入库、chunking/embedding/vector search、基于批准来源的单轮问答、原文引用、基础缺口记录、轻量导出、评估与演示。

**P1 有余力再做**：批量审核、更丰富筛选、中文问答质量优化、可视化研究覆盖图、自动草拟 research note、混合检索或 reranker。P1 不影响 P0 验收，不应挤占第 9–10 天的评估与交付时间。

MVP 使用一个内部工作区和一名当前操作者；以英文公开资料和英文问答作为基线。中文可用于界面与备注，但完整跨语言检索质量不作为首版承诺。

### 3.3 非目标（Out of scope）

- 电力系统仿真、容量计算、接入可行性判定、选址或投资决策；pandapower/OpenDSS 是 Full Stack 角色的独立 technical spike，不属于本 warm-up 的功能、排期或验收。
- 接入电网公司内部系统、实时网络数据、客户机密资料或商业付费数据库。
- 自动批准来源、直接引用未审核网页、在问答时自行联网补足证据。
- 全网爬虫、持续后台监测、无人值守研究代理和自动对外发送报告。
- 扫描 PDF OCR、复杂表格/图表理解、GIS 地图交互、完整数据集分析。可登记相关入口，但首版不从地图或图片中推断容量。
- 多租户、复杂权限、SSO、多人同时编辑、生产级部署与高可用。
- 多轮对话记忆、模型微调、知识图谱和覆盖整个电力行业的知识库。

## 5. 核心工作流

```text
研究主题 / 研究问题
    → 自动生成有限搜索词并调用搜索服务
    → 候选来源列表（去重、标注地区/类型/日期）
    → 查看原文与待审核正文快照
    → 人工 Approve 或 Reject
        → Reject：保留理由，不进入问答知识库
        → Approve：解析检查 → 分块 → embedding → 写入向量索引
    → Ready：可用于检索
    → 用户提问 → 过滤可用来源 → 检索片段 → 生成带引用回答
    → 证据充分：保存答案和引用
    → 证据不足：说明限制 → 记录缺口 → 建议下一轮搜索
    → 人工触发补充搜索，新来源再次经过审核
```

MVP 中“自动发现”指用户启动后系统执行搜索和整理，不要求定时运行。缺口产生后仍由用户决定是否启动下一轮搜索。

**核心不变量**：问答只能使用当前审核有效、版本有效且入库完成的正文片段。搜索摘要、候选资料、被拒绝资料、失败任务和已撤销版本都不能进入问答上下文。

## 7. 来源发现（Source Discovery）

### 7.1 输入与搜索行为

输入包括研究主题、可选研究问题、地区（默认 NZ），以及来源类型。系统生成最多 3 个搜索变体，每轮最多调用 3 次搜索 API，去重后展示最多 10 条候选。少于 10 条时如实显示实际数量，不补造结果。

搜索词优先覆盖 data centre / data center、grid connection / interconnection、large load、hosting capacity、firm / flexible connection、curtailment、N-1 / N-2 等术语。术语扩展不应改变问题的地域、时间或研究对象。

只集成一个搜索服务。提供手动添加公开 URL 的补充入口，该来源同样进入 Pending review；它用于补漏或服务故障时继续整理资料，不能替代自动发现的验收。

### 7.2 来源范围与起点

| 类型 | 搜索方向 | 使用边界 |
| --- | --- | --- |
| 政策、规则与官方指南 | 政府、监管机构、电网公司公开要求 | 区分强制规则、指导材料、征求意见稿与历史版本 |
| 技术文件 | 接入指南、技术标准说明、容量数据说明 | 明确网络、适用地区、负荷/发电场景及条件 |
| 研究论文 | 机构或作者公开论文、开放获取研究 | 保存研究方法、适用范围；结论不直接等同于 NZ 规则 |
| 行业报告 | 研究机构、行业组织、公开研究报告 | 记录作者、出资或商业背景（原文可确认时） |
| 产品与市场材料 | 产品官网、案例和定位说明 | 可支持产品研究，不能作为工程或法规权威依据 |

Brief 提供的研究起点包括 Powerco / Vector capacity maps、EPRI test feeders / DCFlex、Duke Nicholas Institute “Rethinking Load Growth”、Camus Energy 和 Verse；这些是待核查线索，不是已批准来源。[B1，p. 4] Transpower 的公开接入材料可作为 NZ 研究方向，具体文件需搜索后确认。

首轮搜索应覆盖四类核心资料：政策/官方指南、技术文件、论文、行业报告。最终 Ready 语料至少覆盖其中三类；未覆盖的类型要记录原因。交互地图与数据集入口可登记为 `reference_only`，只有可读且经审核的说明文档能参与问答。

### 7.3 候选卡片与排序

每项显示：标题、发布机构、原始 URL、来源类型、地区、发布日期/更新时间、发现时间、主题标签、2–3 句摘要、相关性理由和当前状态。

- 无法确认的发布日期显示“未知”；抓取日期不冒充发布日期。
- 摘要标注依据是“搜索摘要”还是“已获取正文”。搜索摘要不能成为最终问答证据。
- 排序参考问题相关性、原始来源优先级、地区适用性和时效性；显示理由，不显示未经校准的可信度百分比。
- 按规范化 URL 去重；安全地去除跟踪参数但保留影响内容的参数。内容 hash 用于识别相同快照；镜像保留原始出版方优先。
- 每次搜索保存 query、filters、provider、时间、候选数量和错误信息。搜索失败显示可重试错误，不伪装成“没有相关资料”。

## 8. 人工审核（Source Review）

### 8.1 审核操作

审核者查看原始页面、正文预览及元数据，确认与问题的关系、发布主体、地区、日期、正文可读性和使用限制。可修正自动提取的字段，填写备注，再选择 Approve 或 Reject；Reject 必须选择一个简短原因，可补充自由文本。

批准针对**具体内容快照**。允许在审核前抓取和提取正文用于预览，但这部分存储属于候选区，不做 embedding、不加入问答索引。无法获取正文的记录可保留为研究线索，不能批准为可问答资料。

批准表示“允许作为研究证据使用”，并不保证全文正确。商业来源可以批准，但必须保留类型标签及使用限制。

### 8.2 审核与处理状态

审核状态和入库状态分别记录，避免把“已批准”误当成“已经可用”：

| 状态维度 | 值 | 含义 |
| --- | --- | --- |
| Review | `pending` | 等待人工决定 |
| Review | `approved` | 当前内容快照被批准 |
| Review | `rejected` | 不进入问答知识库 |
| Review | `revoked` | 已撤销之前的批准 |
| Ingestion | `not_started / processing / ready / failed` | 分别表示未开始、处理中、可检索、处理失败 |
| Version | `active / superseded` | 当前有效版本，或已被更新版本替代 |

同一文档有更新时，新快照重新进入 Pending；旧的已批准版本可暂时继续使用，但界面提示存在待审核更新。新版本审核并成功入库后才替代旧版本，不悄悄覆盖旧正文。相同 hash 的重复抓取不产生新版本。

撤销批准后，新问答立即排除相关片段；无需等待向量物理删除完成。历史答案保留原引用快照并显示“来源已撤销/已更新”，不当作当前结论重新使用。MVP 不做复杂的版本差异比较。

## 9. 知识库入库、分块与检索

### 9.1 入库流水线

1. 确认来源版本为 Approved，并取得审核时的正文快照及 hash。
2. 检查可解析性，清理页眉页脚、导航和重复空白，保留标题、正文结构、单位与条件。
3. 分块，保存可追溯的原文位置。
4. 用同一个固定 embedding 配置生成文档向量并写入索引。
5. 核对预期 chunk 数量与已写入数量，全部完成后才标记 Ready。

初版支持公开 HTML 与文本型 PDF；建议单文件上限 20 MB、200 页，可配置。超限、加密、扫描件、获取失败或正文为空时显示具体原因。复杂表格若无法保留语义，应跳过对应内容并标注提取限制，不把错位数字写成可靠证据。

入库按文档顺序处理，采用可见进度和显式 Retry，不引入分布式任务队列。保存每次失败阶段；同一版本重试以固定 chunk ID 覆盖或补全，不增加重复向量。

### 9.2 Chunking 与 embedding

- 优先按标题和段落切分。使用本地 embedding 模型对应 tokenizer，起始参数建议 350 tokens/chunk、50 tokens overlap，允许按小型开发集调整。
- PDF 在单页内切分，不跨页拼接。保存 PDF 文件页序（从 1 开始），印刷页码只在可可靠识别时另存。
- HTML 保存章节标题与段落序号；没有真实锚点时不编造链接定位。
- 每块至少包含 `chunk_id`、`version_id`、正文、标题路径、页码或段落定位、内容 hash、embedding 模型及维度。
- 默认本地 SentenceTransformers + `BAAI/bge-small-en-v1.5`（英文，384 维）；问题和文档使用同一固定 revision，并按模型约定区分 query/document。计入特殊 token 后检查模型长度限制，不静默截断。更换配置时重建集合，禁止混用不兼容向量。
- 不跨文档或跨版本拼接 chunk；搜索摘要与模型生成摘要不代替原文分块。

### 9.3 Vector search

先从元数据存储取得 `approved + ready + active` 的版本集合，并应用地区、类型等用户筛选，再在向量库中查询。初始取 Top-10 候选，去除相邻重叠内容后，将最多 5 个相关片段放入生成上下文；不足时使用实际数量。

每次把片段交给模型前，仍核对版本资格，不能只依赖向量库中可能过期的审核标签。无有效版本时直接提示知识库为空，不进行无约束问答。

Top-K 和相似度只用于排序，不等于证据充分或结论正确；不设跨模型通用的“0.8 即可信”规则。地域不匹配、仅有背景定义而缺少所问数字等情况，必须进一步判断证据是否适用。

## 10. 问答与引用（Q&A / Citations）

### 10.1 问答行为

用户提交单轮研究问题，可选地区和资料类型。系统仅依据本次检索到的合格片段生成回答，不将模型常识补写成已证实事实，也不直接联网补充回答。

回答采用固定、简短的结构：

1. **结论或解释**：直接回答有证据支持的部分。
2. **依据**：在具体论断后显示 `[1]`、`[2]` 等引用。
3. **适用范围与限制**：地区、时间、网络、研究假设及未覆盖部分。
4. **待补证据**：必要时建议创建知识缺口，指向下一步搜索。

对复合问题可以部分回答，但要分别标出已支持与未支持的部分。来源冲突时并列显示双方依据及日期，不未经核查就选择其中之一。跨地区资料只能说明其自身范围，不能自动变成 NZ 通用要求。

“最新”“当前”等提问只有在已审核资料能够支持时才给出有时间限定的回答；否则注明“当前知识库尚未验证最新版本”。有获取日期不等于已证明资料仍有效。

对于具体场址可接入 MW、确定接入日期等问题，资料未直接提供所需依据时说明无法确定，不能根据一般术语说明推算答案。

### 10.2 引用要求

| 内容 | 要求 |
| --- | --- |
| 引用位置 | 贴近所支持的事实或结论；不只在答案末尾堆积链接 |
| 展示字段 | 标题、发布机构、原始 URL、发布日期（或未知）、抓取日期、页码/章节/段落 |
| 证据预览 | 点击显示来自已审核版本的原文片段；用户可以打开原文 |
| 内部关联 | 绑定 `answer_id → chunk_id → version_id → source_id` |
| 引用生成 | 模型只返回本次上下文中存在的 chunk ID；服务端验证并组装链接、标题与位置 |
| 翻译 | 原文与译文分开标注；不把生成的中文转述显示为英文原文引语 |

PDF 可提供 `#page=N` 链接，同时在应用内显示对应摘录，以应对浏览器无法准确跳页。HTML 至少显示章节/段落与原文摘录。模型不能自行创造页码、URL、文档名称或引用对象。

引用检查分为两层：程序验证 ID、版本资格和定位是否存在；人工评估引用片段是否真正支持论断。前一层通过不代表答案语义已被验证。

如生成结果引用了不存在或已失效的 ID，最多重试一次；仍失败则显示“无法生成具有有效引用的回答”，保留错误记录。外部服务失败显示服务错误，不误报为知识缺口。

## 11. 知识缺口（Gap Detection）

### 11.1 定义与触发条件

知识缺口表示：**在本次查询范围和当前已审核知识库中，证据不足以回答某个问题或子问题**。它不是对整个行业研究现状的判断，也不证明网上不存在答案。

| 缺口类型 | 触发信号 | 面向用户的后续动作 |
| --- | --- | --- |
| `no_evidence` | 筛选后没有合格资料，或检索内容不涉及问题 | 扩展搜索词，寻找指定主题的公开来源 |
| `partial_coverage` | 仅回答了复合问题的一部分 | 为缺少的子问题补充检索 |
| `jurisdiction_mismatch` | 问 NZ 流程，但现有依据只适用于美国等地区 | 寻找 NZ 官方流程或政策 |
| `freshness_unverified` | 当前性无法确认，或已发现待审核更新 | 核实发布方现行版本 |
| `conflicting_evidence` | 检索片段给出相互冲突的条件或结论 | 并列核查适用范围、版本和发布日期 |
| `needs_external_validation` | 需要场址数据、utility 确认或用户访谈 | 记录要向哪类专家核实什么内容 |

### 11.2 MVP 实现

规则先检查空知识库、筛选后无合格来源等明确情况；模型再根据检索片段给出 `answered / partial / insufficient`、未回答子问题及原因。只检测本次检索上下文中的可能冲突，不声称已扫描整个知识库。

系统自动保存缺口草稿，包含原问题、筛选条件、触发原因、已有证据、缺失证据、建议搜索词和时间。审核者可以编辑或删除误报，状态使用 `open / resolved / dismissed`。同一规范化问题、地区和类型的未解决记录合并，避免反复提问产生重复任务。

至少输出一个可执行建议，例如“查找 NZ 大型负荷接入指南中关于申请资料的章节”，而非笼统说“需要更多研究”。不得将模型猜测出的文件名称当作真实存在的来源。

新增资料获批并入库后，用户重新提问并确认缺口是否已解决；MVP 不自动重跑所有历史问题，也不自动联系外部人员。

## 12. 建议架构

### 12.1 最小实现方案

建议使用 **Streamlit 界面 + Python 服务模块 + SQLite 元数据 + 本地 Chroma 向量库 + 一个搜索服务 + 本地 embedding + ChatGPT 登录授权的生成调用**。这是围绕两周、单操作者、几十份文档的工程选择，不是主项目未来生产架构的承诺。

```text
Streamlit：Discover / Review / Knowledge Base / Ask & Gaps
                         │
                 Python 应用服务
         ┌───────────────┼────────────────┐
   Discovery & Review   Ingestion       Retrieval & Answer
         │               │                │
   Search provider   HTML/PDF parser   Local embedding + ChatGPT OAuth
         │               │                │
         └───────────────┼────────────────┘
                         │
       SQLite（元数据、审核、问答、缺口、任务记录）
       Local files（原文快照与提取正文）
       Chroma（chunk 向量及检索用元数据）
```

| 层 | 建议 | 理由与约束 |
| --- | --- | --- |
| UI | Streamlit，多页或 tabs | 集中实现搜索、表格审核和问答；首版无需另写前端/API 服务 |
| 业务逻辑 | 独立 Python 模块 | 搜索、审核、入库、问答分开，后续需要时再包装 API |
| 元数据 | SQLite | 作为审核状态与版本资格的唯一权威记录；首版仅单写入流程 |
| 正文 | 本地受控目录 | 保留原始快照、hash 和提取结果，使引用可复现 |
| 向量检索 | Chroma 本地持久化 | 根据 version ID 和元数据过滤，仅保存批准内容的向量 |
| 抓取解析 | 一个 HTTP 客户端、HTML 正文提取器、文本型 PDF parser | D1 用实际文件验证解析质量；不引入 OCR |
| 外部搜索 | 一个具有程序接口的搜索服务 | D1 选定账户、结果字段、配额和单次调用上限 |
| 向量模型 | 本地 SentenceTransformers/BGE | 初次下载后固定缓存和 revision；入库和检索不调用云端 embedding |
| 生成模型 | ChatGPT OAuth 订阅授权 + Responses | 用户登录、同意 plan usage、从可用目录选择模型；流完成后校验结构和引用 |
| 评估 | 本地 JSON/CSV 案例与评分记录 | 不开发单独评估平台；Markdown 汇总结果 |

Chroma 官方资料说明可使用 PersistentClient 做本地持久化，并在查询中使用元数据过滤；本方案据此选择它作为小型索引。审批状态仍以应用元数据为准。[Chroma Python client](https://docs.trychroma.com/reference/python)、[Metadata filtering](https://docs.trychroma.com/docs/querying-collections/metadata-filtering)。

Streamlit 的交互会触发脚本重新运行，缓存可减少重复计算。实现时应缓存可复用资源；审核状态和检索资格必须实时校验，不能因缓存而继续使用已撤销内容。[Streamlit caching](https://docs.streamlit.io/develop/concepts/architecture/caching)。

用户已选择本地网页 + ChatGPT 订阅授权 + 本地 embedding。D1–D2 确认账户资格和最小真实生成调用，记录计划用量限制；搜索服务仍独立配置。未登录时可搜索、审核与入库，生成 live 答案需要授权。具体登录、刷新与流式请求约定见开发规格 3.3–3.4 节。

### 12.2 ChatGPT 登录与使用边界（P0）

使用官方 Sign in with ChatGPT 的本地个人应用 plan usage 流程；适用账户资格、授权和额度以实际账户为准。用户通过 Continue with ChatGPT 授权模型调用，界面显示当前账户、可用模型、重新授权与退出。登录成功但未同意使用计划额度时不能生成答案。[官方说明](https://developers.openai.com/siwc/token-sharing-open-source)

登录采用 OAuth PKCE 与本机 loopback callback；tokens 存受保护的本地用户目录，不能进入研究库、浏览器、日志或导出。生成发送到公开 Responses endpoint，要求 stream=true/store=false，并等待完成事件后校验答案。额度耗尽、权限不足、失效或断流显示为服务问题，不能冒充证据不足。[登录](https://developers.openai.com/siwc/token-sharing-open-source/sign-in)、[调用与限制](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)

这仍是本地浏览器网页，首版不转为公网托管、商业网站或 ChatGPT 内部 GPT。公开托管/付费产品需要重新核对适用资格。ChatGPT 订阅不代表无限用量，也不覆盖外部搜索服务费用。[计划使用说明](https://developers.openai.com/siwc/token-sharing-open-source)

### 12.3 可靠性与运行边界

- **可恢复**：持久化入库阶段和错误；重启后识别中断任务，允许人工 Retry。
- **一致性**：向量全部写入后才发布 Ready；撤销先更新 SQLite，再清理索引。检索及答案呈现前核验资格；中途失效则重新检索或终止回答。
- **成本**：固定每轮查询数、候选数、文件大小、上下文上限和最多一次生成重试；记录调用次数、tokens（服务可提供时）与可获取的费用信息。不预设未知 API 单价。
- **服务错误**：对限流和临时故障采用有限重试，最终显示具体失败阶段，不无限重试。
- **访问范围**：运行于本地或既有内部受限环境，不暴露无认证的公网实例。
- **内容与凭证**：搜索 key 与 OAuth tokens 留在本地受保护配置，不进入代码、研究数据库、导出或日志；本次只处理公开资料。
- **外部正文**：始终作为证据数据，不作为工具操作指令；不允许文档中的文字改变审核规则、触发外部请求或泄露配置。
- **URL 获取**：只接受公开 HTTP(S)，拒绝本机/私网地址并检查重定向目标；不绕过登录或付费限制。保存原始链接，受限制资料仅登记线索。

性能是测量目标而非上线 SLA：在固定演示设备与网络下记录一次完整搜索、10 份文档入库和 12 次问答的耗时。交互处理应有即时状态提示；常见单问答以 30 秒内完成为优化目标，外部服务等待需单独记录。

## 13. 最小数据模型

以下是逻辑实体，可用 SQLite 表配合 JSON 字段实现；标签、筛选条件、缺失子问题等不必拆成复杂关系表。

| 实体 | 关键字段 | 作用 |
| --- | --- | --- |
| `SearchRun` | `id, topic, queries, filters, provider, started_at, status, error` | 追踪一次自动发现 |
| `SearchHit` | `search_run_id, source_id, rank, snippet, relevance_reason` | 同一来源可被不同搜索发现；保存当次结果 |
| `Source` | `id, canonical_url, original_url, title, publisher, source_type, jurisdiction, topics, access_status` | 表示来源身份与可人工修正的目录信息 |
| `DocumentVersion` | `id, source_id, content_hash, published_at, fetched_at, raw_path, text_path, review_status, ingestion_status, version_status, extraction_notes, metadata_snapshot` | 固定被审核内容和引用元数据，未知日期允许为空 |
| `ReviewEvent` | `id, version_id, action, reviewer_label, reason, created_at` | 审核、拒绝、撤销等操作历史；操作者标签不等于用户权限系统 |
| `IngestionRun` | `id, version_id, stage, attempt, expected_chunks, indexed_chunks, error, timestamps` | 失败恢复与 Ready 判定 |
| `Chunk` | `id, version_id, ordinal, text, heading_path, page_start, page_end, paragraph_locator, content_hash, embedding_model, embedding_dimension, index_generation` | 原文与向量的桥梁，页码/段落按格式二选一 |
| `QARecord` | `id, question, filters, answer, evidence_status, context_chunk_ids, model_id, output_mode, account_registration_ref, prompt_version, index_generation, created_at, latency, usage` | 重现某次回答使用的上下文和配置 |
| `Citation` | `qa_id, claim_ref, chunk_id, quoted_span, locator_snapshot` | 将具体论断连到证据；`claim_ref` 可用句子序号或稳定标记 |
| `KnowledgeGap` | `id, qa_id, question, scope, reason_type, missing_evidence, suggested_queries, status, resolution_note, created_at` | 管理缺口与补证据过程 |
| `EvaluationRecord` | `id, case_id, qa_id, expected_evidence, reviewer, scores, notes` | 保存人工评估，可先用文件记录 |

```text
SearchRun 1 ─ N SearchHit N ─ 1 Source
Source 1 ─ N DocumentVersion 1 ─ N Chunk
DocumentVersion 1 ─ N ReviewEvent / IngestionRun
QARecord 1 ─ N Citation N ─ 1 Chunk
QARecord 1 ─ N KnowledgeGap
QARecord 1 ─ N EvaluationRecord
```

最低数据约束：同一来源的相同内容 hash 不重复建版本；chunk ID 可确定性重建；只有 Ready 的版本可发布到查询路径；一个来源最多有一个 Active 且 Ready 的批准版本；历史引用不因更新而重新指向其他正文。

AuthRegistration 是受保护本地配置记录，保存已验证身份、issued client ID、host ID、tokens/scopes/expiry；不进入研究数据库。QA 仅记录 opaque 注册引用与实际输出模式，不存 email 或凭证。

## 14. UX 与页面

首版采用四个研究页面，共用账户侧栏（登录、当前账户、模型、退出、Usage 链接），不要求独立首页或复杂 dashboard。面向使用者展示“待审核、处理中、可用于回答、处理失败”等词，chunk 数量和模型配置放在可展开详情里。

| 页面 | 核心内容与操作 | 必须呈现的状态 |
| --- | --- | --- |
| **Discover** | 主题/问题输入、地区和类型筛选、Search、候选列表、手动添加 URL | 搜索中、无结果、服务错误、重复来源提示 |
| **Review** | 待审核列表、正文预览、元数据编辑、Approve / Reject、备注与历史 | 正文不可访问、日期未知、正文提取有限、已审核 |
| **Knowledge Base** | 已批准资料及处理状态、类型/地区筛选、来源详情、Retry、撤销批准、导出 | Approved 但未 Ready、处理中、Ready、Failed、存在新版本 |
| **Ask & Gaps** | 提问、筛选、答案、引用侧栏或展开区、历史问答、缺口列表 | 空知识库、部分回答、证据不足、冲突提示、引用失效 |

关键交互：审核单份资料无需在多个页面间反复跳转；Approve 后显示“已批准，正在处理”，Ready 后才提示可提问；引用点击后同时看到原文摘录和来源链接；缺口记录可编辑、关闭或一键把建议词填入 Discover，但搜索仍由用户触发。

Research log 导出至少包含导出时间、来源目录与审核备注、所选问答及引用、未解决问题。导出不包含密钥、运行日志或未经批准的正文。候选来源如需列出，必须单列为“待审核线索”，不得混入证据清单。

## 15. 评估方案与研究题库

### 15.1 评估准备与方法

建立 15 个研究问题，其中 R01–R12 用于正式问答评估，R13–R15 支持后续研究与团队讨论。D2 记录预期资料类型；D5 前由人工查阅文档，给正式案例写出可接受要点、必须保留的限制和至少一个参考段落。

R01–R08 在固定语料中应有依据；若实际找不到，记录缺口并在 D5 冻结前调整案例及理由，不能虚构标准答案。R09–R12 是刻意保留证据不足的案例，其答案标签取决于冻结语料，不是对全网信息的判断。

用额外的 2–3 个开发问题调整 chunk 大小、Top-K 和提示词；D9 对冻结的 12 个案例做正式评估。为每次运行记录语料版本、模型、提示词和检索参数。修复后重跑受影响案例；如果只优化了同一题库，应注明这是小样本回归评估，不代表普遍准确率。

### 15.2 问题清单

| ID | 研究问题 | 预期行为 / 证据要求 |
| --- | --- | --- |
| R01 | How does a large customer get connected to the grid in New Zealand? | 按资料覆盖范围解释流程，区分 transmission 与 distribution 路径，避免声称所有公司流程完全相同 |
| R02 | Who is involved in the connection process, and what does each party do? | 引用机构职责或流程文件，区分申请方、电网/配电方及其他资料明确的参与者 |
| R03 | What steps or constraints can delay a large-load connection? | 仅列出有来源支持的环节，区分可能原因与经过测量的延误 |
| R04 | What public capacity information is available from NZ network companies, and in what format? | 列举已审核入口或说明文档、数据格式、日期及限制，不把地图入口等同于完整可分析数据 |
| R05 | What does hosting capacity mean in the sources we have reviewed? | 保留原文定义和适用场景，区分新增负荷与发电接入资料 |
| R06 | How do firm and flexible connections differ in the reviewed material? | 指出资料中的合同/运行条件与地区，不给出跨网络无条件保证 |
| R07 | How is curtailment described as a way to accommodate additional load? | 解释已审核研究中的机制、假设和限制，不输出未验证的 NZ 容量增益 |
| R08 | What do the reviewed sources say about N-1 and N-2 redundancy? | 引用定义与适用边界，不声称可直接由术语推算具体站点容量 |
| R09 | Can a new 100 MW data centre connect at a specified NZ site next month? | 语料缺少站点研究时不回答确定容量或日期；列出所缺信息 |
| R10 | What is the exact available capacity at that substation today? | 无当前站点数据时指出无法确定；不把历史资料作为实时值 |
| R11 | Does this US connection policy automatically apply to New Zealand? | 在仅有美国材料且无 NZ 依据的测试条件下，不断言适用；指出地区证据缺口 |
| R12 | What exact curtailment hours and connection date will the utility offer this project? | 语料无该项目正式条件时拒绝编造数值与承诺；说明需取得何种材料 |
| R13 | Which side, utility or data centre, shows the sharper pain and a plausible champion? | 研究讨论题：区分公开证据、假设和需访谈验证的判断 |
| R14 | What do EPRI DCFlex and the Duke research contribute to our research questions? | 仅在对应材料已批准时回答，归纳方法与适用限制 |
| R15 | What evidence is still missing before choosing a prototype direction? | 基于当前库和缺口记录列出下一步，不宣称穷尽所有行业问题 |

### 15.3 指标、阈值与记录

以下阈值是 MVP 目标，交付时必须填写实际结果；本 PRD 不预填“通过”。

| 指标 | 计算或检查方式 | 通过目标 |
| --- | --- | --- |
| 自动发现相关性 | 3 个冻结查询各审阅前 10 条唯一结果；人工标注与问题及地区是否相关 | 总计至少 30 条结果（跨查询可重复），相关条目 ≥70%；若不足 30 条，报告样本不足，不声称达标 |
| 可用知识库 | 统计 Approved + Ready + Active 的不同资料；镜像不重复计数 | ≥10 份，覆盖 ≥3 类核心资料 |
| 检索命中 | R01–R08 中，最终上下文至少包含一个人工标注的相关依据 | ≥7/8；解释性综合问题另记录缺失的子问题证据 |
| 回答质量 | R01–R08 按 0/1/2 分：错误或无依据 / 部分正确 / 正确且覆盖关键条件 | ≥7/8 获 2 分，其余问题如实列出 |
| 引用覆盖率 | 有引用的可核实实质性论断数 ÷ 全部此类论断数 | 100% |
| 引用支持率 | 原文确实支持该论断的已引用论断数 ÷ 全部已引用论断数 | ≥90%；涉及规则、容量、时限等关键结论不得无依据 |
| 引用可追溯性 | 对正式评估的全部引用检查版本、原文摘录与位置 | 100% 可定位；失效外链仍需有受控的已审核快照证据 |
| 证据不足处理 | R09–R12 是否明确不确定、不编造数字/承诺，并列出缺失证据 | 4/4 通过 |
| 缺口可操作性 | 人工检查原因、范围、后续动作是否具体且合理 | ≥3 条经人工确认的有效缺口 |
| 未批准内容泄漏 | 检查待审核、拒绝、撤销、未完成入库的测试资料是否进入上下文 | 0 次 |

发现相关性衡量搜索结果是否相关，不等于已证明来源权威或可以批准。回答正确性和引用支持率优先由另一名团队成员评分；若只能自评，在报告中明确这一限制。对全部正式回答逐条拆分并审查可核实论断，同时报告分子、分母和样本量，避免只给百分比。

### 15.4 必测异常与完整性场景

1. **未批准内容隔离**：在 Pending / Rejected 资料中加入可辨识的测试内容，直接检查最终上下文不包含它。
2. **撤销后生效**：对刚用于问答的来源撤销批准，再提同样问题；不再检索它，历史答案显示失效提示。
3. **重复与重试**：重复添加同一 URL、重新执行失败任务，不增加重复版本或 chunk。
4. **解析失败**：扫描 PDF、空正文或损坏文件显示 Failed，不出现 Ready。
5. **引用校验**：不存在的 chunk ID 被拒绝；有效 ID 对应的片段仍需人工检查支持关系。
6. **来源指令干扰**：正文出现要求忽略规则或调用工具的文字时，仅当作待分析文本，不改变审核和问答行为。
7. **重启与版本更新**：重启后状态和引用仍可追溯；新版本需重新审核，旧答案的引用不被替换。

| ID | 给定 / 操作 | 应观察到的结果 |
| --- | --- | --- |
| AC-01 | 输入 3 个固定研究主题，分别启动搜索 | 真实调用搜索服务；每轮最多 10 个去重候选，字段及搜索记录齐全；按第 15 节报告相关性与样本量 |

| AC-04 | 对含 Pending、Rejected、Revoked、Failed 记录的库查询 | 只有 Approved + Ready + Active 内容进入上下文；重复入库不产生重复检索结果 |
| AC-05 | 在冻结语料和配置上运行 R01–R12 | R01–R08 至少 7 个达到 2 分；R09–R12 全部正确处理证据不足；记录所有失败，不只展示最佳答案 |
| AC-06 | 打开正式评估答案中的每一处引用 | 引用 100% 可追溯，覆盖率 100%，语义支持率 ≥90%，没有无依据的关键工程/规则/时间结论 |
| AC-07 | 触发无证据、范围不匹配或未回答子问题 | 产生可编辑的缺口草稿；至少 3 条被人工确认；有明确下一步，相同未解决缺口不重复堆积 |
| AC-08 | 从应用导出研究记录 | 生成可打开的 Markdown，包含来源目录、审核信息、带引用问答和开放问题；不存在密钥或混入证据区的未批准正文 |
| AC-09 | 撤销、更新、重启、重复提交和失败重试 | 状态与引用持久有效；撤销即时阻止新回答使用；更新需要新审核；关键异常场景均留有结果记录 |
| AC-10 | 按运行说明在已配置环境启动并执行 demo | 核心路径完整可重复；Ready 文档和评估达到第 15 节目标；限制、依赖、实际耗时与遗留问题明确记录 |

## 17. 风险与应对

| 风险 | 影响 | 两周内的应对 |
| --- | --- | --- |
| ChatGPT 授权/资格不可用或计划额度耗尽 | live 生成无法验证 | D1–D2 做官方授权 spike；区分权限与额度问题，停止无效重试，记录未通过；离线实现可继续 |
| 本地模型缺缓存或内存不足 | 无法入库/检索 | 显式下载并锁定 revision；CPU 小批推理，检查 token 长度，禁止静默换模型 |
| 搜索服务、账户或配额不可用 | 自动发现无法验证 | D1 完成真实 API 调用；保存成功搜索样本供回放。手动 URL 可继续研究，但不能据此声称自动发现通过 |
| 自动搜索偏向营销内容或重复转载 | 资料相关但证据质量弱 | 优先原始发布方；人工审核类型、地区与用途，去除重复镜像 |
| 正文提取破坏表格、单位或页码 | 引用看似存在，实际内容错误 | 用 HTML 与 PDF 样本核查；受损部分不入库，标明提取限制 |
| NZ 与海外规则、负荷与发电资料混淆 | 产生错误适用结论 | 元数据标注、问题筛选和回答限制同时保留；专门设置地域错配案例 |
| 过时来源被表述为当前事实 | 研究误导 | 区分发布/抓取日期，保留版本，遇到“最新”问题明确时效限制 |
| 幻觉或引用不支持论断 | 无法信任研究结论 | 控制生成上下文，校验引用 ID，逐条人工评估，证据不足时部分回答或拒绝结论 |
| 审核状态与向量索引不同步 | 被撤销内容泄漏 | SQLite 为资格依据；索引写入完成前不可用；检索和输出前复查 |
| 资料中夹带操作指令 | 干扰模型行为 | 资料仅作为证据；生成阶段不提供搜索、文件写入或发送工具；执行异常测试 |
| 缺口提示过多或过度自信 | 增加研究负担 | 保留原因、范围、去重、人工 Dismiss；只声称当前库缺证据 |
| 两周范围膨胀 | 闭环或评估无法完成 | D5 做端到端检查，推迟全部 P1；不扩展到仿真、地图解析或生产平台 |
| 题库太小或开发者自评 | 夸大质量 | 报告样本数、失败案例与评审者；有条件时请队友独立评分 |

### 19.1 演示准备

## 20. 后续扩展

完成并评估 MVP 后，再根据具体失败类型决定是否推进：

| 扩展 | 触发条件 | 预期价值 |
| --- | --- | --- |
| 混合检索与 reranking | 专有名词、标准编号或精确数字问题经常漏检 | 提高检索相关性，再用原题库比较收益 |
| OCR 与表格解析 | 高价值资料主要是扫描件或结构化表格 | 扩大可用资料范围，同时增加版面与数值校验 |

| 多用户审核与权限 | 多名研究者开始持续协作 | 分工审核、评论和共享历史 |
| 更广的地域与跨语言支持 | NZ 基线稳定，有明确美国比较或中文使用需求 | 保留地区适用边界并单独评估语言质量 |
| 结构化流程与证据比较 | BA/UX 反复需要比较多个网络的接入流程 | 从已审核证据生成可编辑草稿，由人核实 |

| 产品化与独立 API | 有稳定用户、实际使用量和部署需求 | 再考虑独立前端、服务 API、集中式数据库与访问控制 |

任何扩展都需先明确用户收益、额外成本和新的评估要求，不能仅因为技术可用就加入。
